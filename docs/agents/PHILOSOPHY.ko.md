# 프로젝트 철학 (Project Philosophy)

> 이 문서는 [PHILOSOPHY.md](./PHILOSOPHY.md)의 한국어 번역본입니다. 원문이 변경되면 이 문서도 함께 갱신해야 합니다.

사소하지 않은 작업의 범위를 정하기 전에 이 파일을 먼저 읽으십시오. 서사에서 벗어난(off-narrative) 작업 대부분은 이 문서를 건너뛴 데서 나옵니다.

Langflow는 **비주얼 플로우 빌더가 최우선**입니다. 모든 변경은 "캔버스에 노드를 드래그하는 것"만이 유일한 인터페이스인 사람에게 의미가 있어야 합니다. 작업 범위를 정할 때 아래 원칙들을 기준으로 삼고, 제안된 변경이 이 중 하나라도 어긋난다면 멈추고 다시 생각하십시오.

## 원칙 (Tenets)

1. **플로우는 사용자 자산이지 구현 세부사항이 아닙니다.** 플로우 JSON은 사용자의 데이터베이스에 저장되어 프로덕션에서 실행됩니다. 컴포넌트의 하위 호환성은 타협 대상이 아닙니다: 클래스 이름, `name` 속성, input 이름, output 이름을 절대 변경하지 마십시오. input이나 output을 제거하지 마십시오. output 타입을 좁히지 마십시오. `LCModelComponent` 같은 기본 클래스에서 메서드를 제거하지 마십시오. 컴포넌트를 변경하려면 새 컴포넌트를 옆에 추가하고, 기존 컴포넌트에 `legacy=True` + `replacement=[...]`를 설정하고, 저장된 플로우가 계속 로드되도록 테스트의 `file_names_mapping`을 갱신하십시오. 전체 계약 목록은 [CONTRACTS.md](./CONTRACTS.md)를 참고하십시오.

2. **모든 백엔드 기능은 캔버스에 드러나야 합니다.** 어떤 기능이 Python을 모르는 사용자가 연결할 수 있는 컴포넌트(또는 컴포넌트의 속성)로 표현될 수 없다면, 그것은 SDK 기능이며 `langflow-base`가 아니라 `lfx`에 속합니다. 시각적 표면이 없는 백엔드 변경은 거의 항상 서사에서 벗어난 작업입니다.

3. **작업의 단위는 엔드포인트나 서비스가 아니라 컴포넌트입니다.** 라우트, 스토어, 서비스를 추가하기 전에 자문하십시오: 이것이 어떤 컴포넌트를 위한 것인가? 답이 "아직 없다"라면 그 라우트는 시기상조입니다. 컴포넌트나 UI 소비자가 없는 새 REST 엔드포인트는 서사에서 벗어난 작업입니다.

4. **`lfx`는 런타임, `langflow-base`는 플랫폼, `langflow`는 배포판입니다.** 컴포넌트와 그래프 엔진은 `lfx`(`src/lfx/src/lfx/components/`)에 있습니다. API, 인증, 영속성, 멀티 유저 관심사는 `langflow-base`에 있습니다. `langflow` 패키지는 이 모든 것을 함께 담아 배포하는 통합체입니다. 새 코드는 그것을 담을 수 있는 가장 낮은 계층에 둡니다. 경계는 단방향으로 강제됩니다: `langflow` → `langflow-base` → `lfx`. [ARCHITECTURE.md](./ARCHITECTURE.md)를 참고하십시오.

5. **빌더 사용자가 노드에서 설정할 만한 것에 config 플래그를 추가하지 마십시오.** 어떤 설정이 플로우 동작에 영향을 준다면 그것은 컴포넌트 input입니다. 배포에 영향을 준다면 환경변수입니다. 컴포넌트의 의미를 바꾸는 숨은 전역 플래그는 "보이는 데이터 흐름" 계약을 깨뜨립니다.

6. **보이는 데이터 흐름이 영리한 마법보다 낫습니다.** 암묵적 컨텍스트, 숨은 전역 상태, 사이드 채널 상태는 캔버스에서 플로우를 읽을 수 없게 만듭니다. 데이터는 input과 output을 통해 전달하십시오. 전역 변수에 손이 간다면, 노드에 속하지 않는 무언가를 만들고 있을 가능성이 높습니다.

7. **기능 확장보다 조합(Composition)을 우선하십시오.** 여러 모드를 가진 하나의 큰 컴포넌트보다, 사용자가 연결해서 쓸 수 있는 작고 단일 목적의 컴포넌트를 추가하는 쪽을 선호하십시오. `If-Else` / `Current Date` 스타일(한 가지 일, 명확한 이름, 직관적인 아이콘)이 목표 형태입니다.

8. **모든 컴포넌트에는 `display_name`, `description`, `icon`, 그리고 적절한 카테고리가 필요합니다.** 사이드바에서 알아보기 어렵게 렌더링되는 컴포넌트는 출시되면 안 됩니다. 아이콘은 장식이 아니라 API의 일부입니다 — 동작(동사)에 어울리는 Lucide 아이콘을 고르십시오.

9. **Playground는 빌더 사용자가 보는 테스트 하네스입니다.** 컴포넌트는 유닛 테스트가 통과할 때가 아니라, 캔버스 위의 플로우에서 끝까지(end-to-end) 동작할 때 "완성"입니다. 기능이 동작한다고 주장하기 전에 Graph 테스트 패턴(빌드, `.set()`, `async_start`, 검증)을 사용하십시오.

10. **두 부류의 사용자, 하나의 제품: 비주얼 빌더와 Python 개발자.** 두 요구가 충돌하면, `langflow-base` 기능에서는 비주얼 빌더가, `lfx` SDK 기능에서는 Python 개발자가 우선입니다. SDK를 예쁘게 만들려고 캔버스를 희생하지 말고, 캔버스를 쉽게 만들려고 SDK를 희생하지 마십시오.

11. **변경이 무언가를 고쳤다는 증거가 없다면 그것은 수정(fix)이 아닙니다.** 에러 핸들링 추가, 재시도 추가, 타입 확장, 불안정한 테스트 건너뛰기는 수정이 아닙니다. 실패를 재현하고, 수정이 그 실패를 제거함을 입증한 뒤에 배포하십시오. [ANTI-PATTERNS.md](./ANTI-PATTERNS.md)를 참고하십시오.

## 적용 방법

작업 범위를 정할 때 위 원칙들을 훑으며 그 작업이 어떤 원칙에 봉사하는지 이름을 대보십시오. 변경이 원칙 1, 2, 3에 어긋난다면, 코드를 쓰기 전에 멈추고 그 충돌을 드러내십시오. 어떤 원칙에 봉사하는지 알 수 없는 변경이라면 십중팔구 서사에서 벗어난 작업입니다 — 질문하십시오.
